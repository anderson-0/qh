# qh — design spec

Date: 2026-10-09
Status: approved in conversation, pending written-spec review

## 1. Purpose

qh is an MCP server that lets AI agents explore and query databases. It is a
from-scratch Go replacement for [bytebase/dbhub](https://github.com/bytebase/dbhub)
that aims to be better on four measurable axes:

1. **Fewer tokens** per task (tool definitions + tool results).
2. **Better answers** (agents find the right tables, joins and values first time).
3. **Faster** (schema discovery and queries).
4. **Connections managed by API**, not config files, and usable by agents
   immediately without a restart.

### Why dbhub leaves room (findings from reading dbhub `main` @ `116cfdd`)

| dbhub behaviour | Effect | qh answer |
|---|---|---|
| Results are pretty-printed JSON with keys repeated on every row | ~3.5–4× more tokens than TSV for a 50×7 result (estimated) | TSV + one-line footer |
| Each source registers its own `execute_sql_<id>` / `search_objects_<id>` | Tool-definition tokens grow linearly with connections | 2 tools total; `source` is a parameter |
| `max_rows` is opt-in per tool | An unbounded `SELECT *` can flood the context | 100-row default cap on every connection |
| `search_objects` summary/full runs 3–4 queries per table, sequentially, uncached; falls back to `COUNT(*)` | Slow on large schemas | ~5 bulk catalog queries per connection, run in parallel and cached |
| No foreign keys or enum values in schema output | Agents guess joins/values, then retry | FKs in both directions + enum values inline |
| HTTP API is read-only (`GET /api/sources`, `/api/requests`); sources come from TOML + file watcher | No programmatic registration; tool list cached by clients for up to 5 min | Full CRUD REST API; the tool list never changes |

### Who it is for

All four deployment shapes, served by one binary:

- a local developer tool (stdio or loopback HTTP, zero config, no auth);
- a self-hosted server for one team;
- a shared multi-team service;
- the backend of a product that registers its customers' databases.

The unifying concept is the **workspace**: local mode has one implicit
`default` workspace; server mode has many, isolated from each other.

### Success criteria

- Benchmark vs dbhub (§9): ≥40% fewer total tokens per task, accuracy ≥ dbhub,
  fewer tool calls per task.
- All tool definitions together cost ≤ 800 tokens (measured with the
  Anthropic token-counting endpoint).
- Cold schema build on a 1,000-table Postgres database < 1 s.
- A connection created through the API is queryable by an already-connected
  agent on its next tool call, with no restart and no tool-list change.

## 2. Scope

### In v1

- Engines: PostgreSQL (13–17), MySQL 8 / MariaDB 11, SQLite.
- Transports: MCP over stdio and over Streamable HTTP; REST API; CLI.
- Connection details: connection string or structured fields, plus TLS options.
- Per-connection read-only (default) or read-write mode.
- Workspaces, scoped API keys, encrypted credentials, query log.

### Not in v1 (designed so they can be added without changing tools)

- NoSQL engines (MongoDB first) — see §4.4 for how the interfaces accommodate them.
- SQL Server, Oracle.
- SSH tunnels, cloud IAM auth, secret-manager references (`env:`, `aws-sm://`).
- Web UI (the OpenAPI spec is published so one can be built later).
- Multi-statement scripts; write approval workflows.
- Restricting a key to specific connections inside a workspace.
- Running several server instances against one store (needs a Postgres-backed
  `Store`; the interface allows it).
- Prometheus metrics.
- Importing dbhub TOML files.

## 3. Agent-facing surface (MCP)

### 3.1 Tools

| Tool | Inputs | Returns |
|---|---|---|
| `schema` | `source` (optional when the workspace has one connection), `pattern` (optional, `*` wildcard, case-insensitive), `object` (optional, exact name, optionally `namespace.name`) | No arguments: the connection list (`name engine ro/rw — description` per line) when the workspace does not have exactly one connection, else the overview. `pattern`/`object`: detailed definitions of matching objects |
| `query` | `source` (optional when the workspace has one connection), `query` (required); `max_rows` (optional, ≤ connection cap); `explain` (optional bool) | Result as TSV + footer, or the execution plan when `explain` is true |

The server's MCP `instructions` field carries one short hint (query directly
when the names are known, otherwise call `schema` first; errors on unknown
names suggest close matches) and names the
workspace's connections, up to 20, each description clipped to 60
characters. They are built at each `initialize`, so a new session sees the
current connections.

Tool descriptions are written tersely; total definitions ≤ 800 tokens is a
test assertion (§9).

### 3.2 `query` output

```
id	email	plan	created_at
1	a@x.com	pro	2025-03-14T10:22:31Z
…
-- 100 rows shown, more exist (truncated) · 38ms
```

- Header row, then rows. Footer forms:
  - `-- 12 rows · 8ms`
  - `-- 100 rows shown, more exist (truncated) · 38ms`
  - `-- 3 rows affected · 12ms` (writes)
- Cell rendering:
  - `NULL` for null;
  - booleans `true`/`false`;
  - timestamps RFC 3339;
  - numbers in the database's own text form, so no precision is lost;
  - JSON and array values as compact JSON;
  - binary as `<bytes 2.1KB>`;
  - `\t`, `\n`, `\r` and `\\` escaped;
  - values longer than 200 characters are cut, with `…[+N chars]` appended.
- Row cap: `max_rows` argument, else the connection's `max_rows` (default 100,
  hard maximum 10,000). Truncation is detected by fetching `cap + 1` rows (§4.2).
- `explain: true` returns the engine's plan without running the query:
  - Postgres: `EXPLAIN (FORMAT TEXT)`;
  - MySQL: `EXPLAIN FORMAT=TREE`;
  - MariaDB: tabular `EXPLAIN` rendered as TSV;
  - SQLite: `EXPLAIN QUERY PLAN`.

### 3.3 `schema` output

Overview (no `pattern`/`object`), at most 200 objects, then per-namespace totals:

```
public: 42 tables, 3 views
  orders ~1.2M · order_items ~4.8M · users ~90k · …
analytics: 12 tables
  …
-- showing 200 of 1,240 objects; use pattern= to narrow
```

Detail (with `pattern` or `object`):

```
public.orders ~1.2M rows: Customer orders
  id bigint PK
  user_id bigint NN → users.id
  status order_status NN [pending|paid|shipped]
  total numeric(10,2)
  created_at timestamptz NN =now()
  ← order_items.order_id, refunds.order_id
  idx (user_id) (status,created_at)
```

- `PK` primary key, `NN` not null, `=expr` default.
- `→` foreign key out; `←` foreign keys pointing in.
- `[a|b|c]` enum values (Postgres enums, MySQL `ENUM`); omitted for CHECK constraints in v1.
- The comment follows the `:` on the header line; column comments follow a trailing `# `.
- Row counts come from catalog estimates, never `COUNT(*)`.
- Detail output covers at most 30 objects per call. Past that, it lists the
  names and asks the agent to narrow the pattern.
- Connections with `allowed_namespaces` show only those namespaces, in both
  `schema` and the suggestions in §3.4.

### 3.4 Errors

Every error is one line: `error[<category>]: <message>. <hint>`.
MCP returns it as a tool result with `isError: true`.

| Category | When |
|---|---|
| `auth` | Missing or invalid key |
| `forbidden` | Key lacks the needed scope |
| `unknown_source` | No such connection (the message lists the available names) |
| `invalid` | Bad arguments |
| `read_only` | A write was attempted on an `ro` connection |
| `timeout` | Query exceeded the connection's timeout |
| `connection_failed` | Can't reach the database (host shown, secrets never) |
| `query_error` | The database rejected the query |
| `busy` | A concurrency limit was reached and the wait timed out |

**Suggestions.** Unknown-column and unknown-table errors are recognised by
engine error code:
- Postgres `42703` / `42P01`;
- MySQL/MariaDB `1054` / `1146`;
- SQLite `no such column` / `no such table`.

They get "did you mean" candidates from the cached catalog, using
case-insensitive edit distance and limited to the tables named in the query.
For example: `error[query_error]: column "email_addr" does not exist. orders has: id, user_id, status, …; users has: email`.

**Scrubbing.** Before any driver error is returned or logged, it is scrubbed of
the connection's password and full connection string.

## 4. Architecture

### 4.1 Packages

Module path `github.com/anderson-0/qh`.

```
cmd/qh/                 main; wires CLI commands
internal/engine/        Engine/Conn interfaces, Catalog model, Result model, registry
internal/engine/postgres
internal/engine/mysql   (MySQL and MariaDB; flavour detected at connect)
internal/engine/sqlite
internal/core/          Service: Sources, Schema, Query — enforces policy, used by MCP and REST
internal/format/        TSV result renderer, schema renderer, JSON renderer (REST)
internal/catalog/       schema cache (TTL, singleflight, invalidation)
internal/pool/          connection pool manager (lazy open, idle close, global cap, versioned swap)
internal/suggest/       did-you-mean matcher
internal/store/         Store interface + SQLite implementation + migrations
internal/secret/        AES-256-GCM sealing, master-key loading and rotation
internal/auth/          API key parsing, hashing, scope checks
internal/netguard/      dial-time address policy (§6.4)
internal/mcpserver/     MCP tool registration over the core service
internal/api/           REST handlers, problem+json, OpenAPI document
internal/cli/           conn / key / workspace / masterkey commands (local store or remote API)
bench/                  benchmark harness (separate Go module)
```

**Dependencies.** Each package depends only on packages below it:
`mcpserver`/`api` → `core` → (`engine`, `catalog`, `pool`, `format`, `suggest`, `store`, `auth`).

Engines depend only on `engine` and `netguard`.

**Libraries:**
- MCP: `github.com/modelcontextprotocol/go-sdk`. During planning, confirm it
  supports stateless Streamable HTTP and the current protocol version.
- Drivers: `pgx/v5`, `go-sql-driver/mysql`, `modernc.org/sqlite` (pure Go,
  so no cgo and a single static binary).
- Integration tests: `testcontainers-go`.
- `go.mod` targets the current stable Go release at project start.

### 4.2 Engine interface

```go
type Engine interface {
    Name() string                                  // "postgres", "mysql", "sqlite"
    Open(ctx context.Context, spec ConnSpec) (Conn, error)
}

type Conn interface {
    Query(ctx context.Context, q string, o QueryOpts) (*Result, error)
    Explain(ctx context.Context, q string) (*Result, error)
    Introspect(ctx context.Context, o IntrospectOpts) (*Catalog, error)
    Classify(q string) (Access, error)             // Read | Write | DDL; error if multiple statements
    ClassifyError(err error) ErrInfo               // category + unknown identifier, if any
    Ping(ctx context.Context) error
    Close() error
}

type QueryOpts struct {
    MaxRows  int           // cap; engine fetches MaxRows+1 to detect truncation
    ReadOnly bool
    Timeout  time.Duration
}

type Result struct {
    Columns      []Column  // name + engine type name
    Rows         [][]any   // at most MaxRows
    Truncated    bool
    RowsAffected int64     // writes; -1 when not applicable
    Duration     time.Duration
}
```

**Row capping, per engine.** The query text is never rewritten.

- **Postgres:**
  1. Every query runs in a transaction: `BEGIN READ ONLY` for `ro`, plain `BEGIN` for `rw`.
  2. `SET LOCAL statement_timeout` is applied inside it.
  3. Row-returning statements that `Classify` marks as `Read` (`SELECT`,
     `VALUES`, `TABLE`, `WITH … SELECT`) are opened as a cursor
     (`DECLARE … NO SCROLL CURSOR`) and read with `FETCH cap+1`. The server
     stops producing rows after that.
  4. Any other statement runs directly, with the driver stopping at `cap+1`
     rows. This includes data-modifying CTEs, which Postgres does not allow
     inside a cursor, `SHOW`, and a bare `EXPLAIN`.
- **MySQL/MariaDB:**
  1. Every query runs in a transaction: `START TRANSACTION READ ONLY` for
     `ro`, plain `START TRANSACTION` for `rw`.
     `SET SESSION sql_select_limit = cap+1` is applied before the statement
     and reset to `DEFAULT` after.
  2. An explicit `LIMIT` in the query takes precedence over `sql_select_limit`,
     so the driver also stops reading at `cap+1` as a backstop. When it stops
     early, the pooled connection is discarded rather than drained.
  3. Timeout: `max_execution_time` (MySQL, milliseconds) or
     `max_statement_time` (MariaDB, seconds), plus the context deadline.
- **SQLite:**
  1. Rows are read one at a time; reading stops after `cap+1`.
  2. Timeout: context cancellation, which interrupts the statement.

**Multiple statements are rejected in v1.** `Classify` returns `invalid` for
input with more than one statement, ignoring a trailing `;`.

### 4.3 Catalog model and cache

```go
type Catalog struct {
    Namespaces []Namespace
    BuiltAt    time.Time
}
type Namespace struct{ Name string; Objects []Object }
type Object struct {
    Name, Kind, Comment string       // Kind: table | view | matview | collection
    RowEstimate        int64         // -1 unknown
    Fields             []Field
    PrimaryKey         []string
    ForeignKeys        []ForeignKey  // outgoing
    ReferencedBy       []ForeignKey  // incoming, computed after introspection
    Indexes            []Index
}
type Field struct {
    Name, Type, Default, Comment string
    Nullable  bool
    Enum      []string
    Inferred  bool                   // true for sampled document fields (NoSQL)
}
```

**Introspection is bulk and parallel.** A fixed set of catalog queries runs
per connection, never one per table:
- **Postgres** (`pg_catalog`), five queries:
  1. relations with estimates and comments;
  2. columns with types, defaults and comments;
  3. constraints (PK/FK/unique);
  4. indexes;
  5. enum labels.
- **MySQL/MariaDB** (`information_schema`): the equivalent set.
- **SQLite:** `sqlite_schema`, plus `pragma_table_info` / `pragma_foreign_key_list`
  / `pragma_index_list` used as table-valued functions in one joined query.

**Cache:**
- Lives in memory, one per connection, keyed by connection id + version.
- Built on first need: a `schema` call, or an error that wants suggestions.
- If several callers need it at once, one build runs and the others wait for it.
- Rebuilt when any of these happens:
  - 10 minutes pass;
  - a statement classified as DDL succeeds through `query` on that connection;
  - `POST /api/v1/connections/{name}/schema/refresh` is called;
  - the connection's version changes.

### 4.4 NoSQL readiness (not built in v1)

A MongoDB engine will plug in without changing any tool:

- **Tools:** `query.query` holds the engine's native language. For MongoDB that
  is a JSON document such as
  `{"collection":"orders","find":{...},"sort":{...}}` or
  `{"collection":"orders","aggregate":[...]}`.
- **Read/write classification:** `Classify` allows `find`, `aggregate`,
  `count` and `distinct` without `$out`/`$merge` for `ro`, and rejects
  everything else.
- **Schema:** `Introspect` samples documents per collection (default 100,
  using `$sample`). Fields come back as `Inferred`, with union types such as
  `string|null` and dotted paths such as `address.city`. `Kind = collection`.
- **Results:** documents are flattened into columns, using the union of
  top-level keys in the returned rows, so TSV output still works. Nested
  values are rendered as compact JSON.
- **Shared code:** the formatter, cache, pool manager, store, auth, API and
  MCP layers are engine-agnostic. The engine conformance suite (§9) has a
  catalog-only subset that a document engine must pass.

### 4.5 Pool manager

- Pools are keyed by connection id + version and opened lazily on first use.
- Each pool allows 5 open connections by default, configurable per connection.
- A server-wide cap on open database connections (default 500) closes the
  least-recently-used idle pools when reached.
- Pools unused for 10 minutes are closed.
- When a connection's version changes, new requests use a new pool and the
  old pool closes once its in-flight queries finish.
- A query waits up to 10 s for a pool slot before returning `busy`.
- An unreachable database marks the pool unhealthy. The next call retries
  with exponential backoff (1 s → 30 s), and the failure is reported as
  `connection_failed`.

## 5. Data and storage

### 5.1 Store

`Store` is an interface; v1 implements it on SQLite (WAL mode).

**Where the store lives:**
- Local mode: `$QH_HOME`, or `~/.config/qh/`, containing `qh.db` and `master.key`.
- Server mode: `--data-dir`.

**Tables:**
- **`workspaces`:** `id`, `name` (unique), `created_at`.
- **`connections`:**
  - identity: `id`, `workspace_id`, `name`, `engine`;
  - credentials: `secret` (sealed blob), `secret_key_id`;
  - display: `host`, `port`, `database`, `username`;
  - settings: `description`, `mode` (`ro`|`rw`), `max_rows`, `timeout_ms`,
    `pool_size`, `allowed_namespaces` (JSON list, optional), `tls` (JSON);
  - bookkeeping: `version`, `created_at`, `updated_at`.

  `name` matches `^[a-z0-9][a-z0-9_-]{0,63}$` and is unique per workspace.
- **`api_keys`:** `id`, `workspace_id` (null for admin keys), `prefix`,
  `hash` (SHA-256 of the secret part), `scopes`, `name`, `created_at`,
  `expires_at`, `last_used_at`.
- **`query_log`:** `id`, `workspace_id`, `connection_id`, `key_id`, `tool`,
  `query`, `rows`, `duration_ms`, `error_category`, `at`.
  - Retained 30 days by default (`--query-log-retention`).
  - Disabled with `--no-query-log`.
- **`meta`:** `schema_version`, `revision`.

**Change detection.** `revision` increases on every connection or key change.
- Local mode: the CLI can change the store while a separate `qh mcp` process
  is running, so the core service checks `revision` at the start of each tool
  call and reloads what changed.
- Server mode: changes come through the same process, so the service is
  notified directly.

### 5.2 Credentials

- The connection string, password included, is sealed with AES-256-GCM.
  - Format: `key_id || nonce || ciphertext`.
  - Additional authenticated data: the connection id, so a blob copied to
    another row fails to open.
- Master key:
  - server mode: `QH_MASTER_KEY` (base64, 32 bytes), required;
  - local mode: generated at first run into `master.key` with mode `0600`.
- `qh masterkey rotate` re-seals every connection under a new key id. The old
  key must be supplied for the rotation, and is no longer needed afterwards.
- Connection strings are never returned by the API or CLI. Responses show the
  display fields, plus the string with the password replaced by `***`.

## 6. Access control and safety

### 6.1 Modes

| | Local | Server |
|---|---|---|
| Start | `qh mcp` (stdio) or `qh serve` (binds `127.0.0.1:8765`) | `qh serve --http <addr> --data-dir <dir>` |
| Auth | None; the `default` workspace | API key required on every request except `/healthz` and `/readyz` |
| Binding | `qh serve` refuses non-loopback addresses unless started in server mode | — |

### 6.2 API keys and scopes

- Format: `qh_<8-char prefix>_<32-byte secret, base62>`. Sent as `Authorization: Bearer …`.
- The prefix is used to look the key up; the secret's SHA-256 is compared in
  constant time.
- Scopes:

  | Scope | Allows |
  |---|---|
  | `query` | MCP tools; `GET …/schema`; `POST …/query` |
  | `manage` | Connection CRUD and schema refresh in the key's workspace |
  | `admin` | Workspaces and keys in all workspaces; no workspace binding |

- Bootstrap: on first start in server mode with an empty `api_keys` table,
  the server prints one admin key to stderr, once. If `QH_BOOTSTRAP_ADMIN_KEY`
  is set, that value is stored instead.
- An admin key working inside a workspace names it with
  `X-QH-Workspace: <name>`. On MCP, a workspace-bound key always uses its own
  workspace.
- Each key can run at most 4 queries at once; past that, requests wait and
  then return `busy`.

### 6.3 Read-only enforcement (`ro` connections)

1. **The database enforces it:**
   - Postgres: `BEGIN READ ONLY` per query.
   - MySQL/MariaDB: `START TRANSACTION READ ONLY` per query.
   - SQLite: opened with `mode=ro` and `PRAGMA query_only=ON`.
2. **The classifier** rejects writes, DDL and multiple statements before
   sending, so the agent gets a clear `read_only` error.
3. **SQLite `ATTACH`/`DETACH`** are rejected by the classifier for every
   SQLite connection, in both modes. Here the classifier *is* the boundary,
   and the escape tests check it.
4. **Documentation** recommends a database user with read-only grants, and
   lists what read-only transactions cannot stop, e.g. Postgres `dblink` or
   `postgres_fdw` opening a second connection.

### 6.4 Server-mode network and file safety

In server mode, any `manage` key can register a connection, so qh must not
become a way into the host or its network.

- **Address policy.** Engines dial through `netguard`, which checks the
  *resolved* IP at connect time, so DNS tricks can't get around it.
  - Default deny: loopback, link-local (including cloud metadata addresses
    `169.254.169.254` and `fd00:ec2::254`), and unspecified addresses.
  - Override with `--allow-cidr` / `--deny-cidr` (repeatable).
    `--allow-cidr 127.0.0.0/8` restores loopback for self-hosted setups.
  - Private ranges (10/8, 172.16/12, 192.168/16) are allowed by default,
    because self-hosted teams need them; operators can deny them with `--deny-cidr`.
- **SQLite in server mode** is disabled unless `--sqlite-root <dir>` is set.
  Paths must then resolve, after following symlinks, inside that directory.
- In local mode, neither restriction applies.

## 7. REST API (`/api/v1`)

All bodies are JSON. Errors are `application/problem+json` (RFC 9457), with
`type` set to the category from §3.4.

| Method & path | Scope | Notes |
|---|---|---|
| `POST /connections` | manage | Body: `name`, `engine`, then either `dsn` or `host`/`port`/`database`/`username`/`password`/`params`, plus optional `description`, `mode`, `max_rows`, `timeout_ms`, `pool_size`, `allowed_namespaces`, `tls`. Connects and tests first; responds 201 with the connection, `server_version` and `connect_ms`. `?skip_test=true` saves without testing |
| `GET /connections` | query | List (secrets hidden) |
| `GET /connections/{name}` | query | One connection |
| `PATCH /connections/{name}` | manage | Partial update. Tests again if connection details changed. Increases `version` |
| `DELETE /connections/{name}` | manage | Deletes it and closes its pool |
| `POST /connections/test` | manage | Same body as create; nothing is saved |
| `POST /connections/{name}/schema/refresh` | manage | Rebuilds the cache; returns object count and build time |
| `GET /connections/{name}/schema?pattern=&object=` | query | Same as the MCP tool. `Accept: text/plain` (default) or `application/json` |
| `POST /connections/{name}/query` | query | Body `{query, max_rows?, explain?}`. TSV (default) or JSON |
| `GET /query-log?connection=&since=&limit=` | manage | Newest first; at most 1,000 entries per request |
| `GET/POST /workspaces`, `DELETE /workspaces/{name}` | admin | Deleting a workspace removes its connections and keys |
| `GET/POST /keys`, `DELETE /keys/{id}` | admin, or manage for keys in its own workspace with `query`/`manage` scopes | The full key is returned once, at creation |
| `GET /openapi.json` | none | OpenAPI 3.1 document, kept in sync with handlers by a test |

Other endpoints:
- `/healthz`: the process is up.
- `/readyz`: the store is reachable and migrations are applied.
- `/mcp`: MCP Streamable HTTP, stateless.

## 8. CLI

```
qh mcp                                  # stdio MCP server, local store
qh serve [--http addr] [--data-dir dir] # HTTP: MCP + REST
qh conn add <name> --engine postgres --dsn ... [--rw] [--description ...]
qh conn ls | show <name> | rm <name> | test <name> | edit <name> [flags]
qh key create --scopes query,manage [--workspace w] [--expires 90d]
qh key ls | rm <id>
qh workspace create|ls|rm <name>
qh masterkey rotate --old-key-file f
qh query <conn> "<sql>"                 # same output as the MCP tool, for humans and scripts
qh schema <conn> [pattern]
```

Without `--server`, commands work on the local store directly. With
`--server URL --key KEY` (or `QH_SERVER` / `QH_KEY`), they call the REST API.

## 9. Testing and benchmark

### 9.1 Tests

- **Unit tests:**
  - TSV formatter: escaping, truncation, every value type;
  - schema renderer: golden files;
  - classifier, per dialect;
  - error classification and scrubbing;
  - `secret`: round-trip, wrong additional data fails, rotation;
  - `auth`: parsing and scope matrix;
  - `suggest`;
  - `netguard`: CIDR policy, resolved-IP check;
  - `store`, against a temporary SQLite file.
- **Fuzz tests:** TSV formatter and classifier, using Go's native fuzzing.
- **Engine conformance suite.** One shared test suite, run against:
  - Postgres 13 and 17, MySQL 8, MariaDB 11 (testcontainers-go);
  - SQLite in-process.

  The fixture schema has foreign keys, an enum, table and column comments, a
  view, Unicode, nulls, binary data, numbers too large for a float, and
  timestamps with time zones.

  It checks:
  - identical rendered `schema` output, apart from type names, which are kept in per-engine golden files;
  - identical `query` output for the shared queries;
  - truncation detection;
  - timeouts;
  - error categories and suggestions.
- **Read-only escape tests**, which must all fail on `ro` connections:
  - `INSERT` / `UPDATE` / `DELETE`;
  - a CTE that contains `DELETE`;
  - `SELECT … INTO`;
  - `nextval()`;
  - `SET TRANSACTION READ WRITE`;
  - `COMMIT; DELETE …`;
  - SQLite `ATTACH DATABASE`;
  - MySQL `LOAD DATA`;
  - DDL;
  - `SET SESSION TRANSACTION READ WRITE`.
- **Integration tests:**
  - Over REST: create → query over MCP → patch → query → delete, in one
    running server with no restart.
  - **Workspace isolation:** a key from workspace A gets `unknown_source` /
    404 for anything in workspace B, over both MCP and REST.
  - netguard blocks `127.0.0.1` and `169.254.169.254` in server mode.
  - `--sqlite-root` is enforced, including against symlink escapes.
  - The OpenAPI document matches the registered routes.
  - A full MCP session using the go-sdk client over in-memory and HTTP
    transports.
  - Tool-definition size ≤ 800 tokens, using the token-counting endpoint;
    skipped when no API key is configured.
- CI runs with `-race`.

### 9.2 Benchmark (`bench/`, separate Go module)

- **Datasets:** Pagila (Postgres), Sakila (MySQL), Chinook (SQLite), each
  loaded into a container.
- **Questions:** about 30 per dataset, each with a ground-truth answer
  computed by a reference SQL query. The mix:
  - lookups;
  - multi-join questions that need foreign keys;
  - filters on enum values;
  - aggregations;
  - a large-result question where the right move is not to dump rows;
  - one question phrased to invite a misspelled column, testing recovery.
- **Harness:**
  - Drives a current Claude model through the Anthropic API (Go SDK), with the
    server under test as the only tool source.
  - Same model, system prompt and settings for qh and dbhub.
  - 3 runs per question.
  - A second scenario registers 5 connections at once, to measure how the
    cost of tool definitions grows with connections.
- **Metrics:**
  - input/output tokens, from the API's usage fields;
  - tool calls per question;
  - wall time;
  - correctness against ground truth (numeric tolerance 1e-6; sets compared ignoring order);
  - tool-definition tokens.
- **Micro-benchmarks:**
  - cold `schema` build on a generated 1,000-table Postgres database;
  - `query` latency p50/p95 for qh vs dbhub on the same query set.
- **Report:** a Markdown table per dataset, written to `bench/results/<date>.md`.
- **Release gate:** the success criteria in §1.
